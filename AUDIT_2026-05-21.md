# Audit 2026-05-21: multi-backend bugs in `braincoder.utils.backend`

A systematic re-read of `braincoder/utils/backend.py` (the backend-agnostic
abstraction over Keras 3 / TF / JAX / PyTorch) turned up four bugs that
silently produced wrong results, biased gradients, or leaked memory.
All four were paired with regression tests in
`tests/test_backend_multibackend.py` that exercise every backend in the CI
matrix (`.github/workflows/tests.yml`).

## Bug 1 - `safe_cholesky` silently returns NaN on JAX

`safe_cholesky` retries Cholesky with progressively larger jitter on
exception. On JAX, `jnp.linalg.cholesky` does not raise on a non-PSD
input -- it returns a NaN-filled matrix. The first `ops.cholesky` call
therefore bound `L` to NaN and the `break` fired, propagating NaN to
every downstream caller (notably `EncodingModel.get_stimulus_pdf` and
the residual fitter). The Keras 3 wrapper does raise in eager mode on
newer versions, but inside `jax.jit` traces the NaN still escapes
silently.

Fix: after each `ops.cholesky` attempt, explicitly check
`bool(ops.any(ops.isnan(L)))`. Treat a NaN result identically to an
exception (bump jitter, retry). The eager NaN check is wrapped in a
try/except so the function stays usable inside JIT (where it falls back
to the exception path -- see comment in code).

## Bug 2 - `_lgamma` was non-differentiable and JAX-incompatible

`_lgamma` pulled scalars out via `float(ops.convert_to_numpy(...))`,
called `scipy.special.gammaln`, then re-boxed. Two failure modes:
  - **JAX**: under `value_and_grad`, the argument is a `Tracer`, and
    `convert_to_numpy` on a tracer raises `ConcretizationTypeError`.
    Any code path that fits `dof` via `mvt_log_prob` therefore crashed.
  - **TF / torch**: scipy's `gammaln` has no autograd connection, so
    `d nll / d dof` was missing all the `lgamma` contributions. The
    fitted dof was biased.

Fix: route through the public `lgamma` function (defined below in the
same file), which uses backend-native `tf.math.lgamma`,
`jax.scipy.special.gammaln`, or `torch.lgamma`. Single-line edit;
function value is unchanged but the autograd graph is now connected.

## Bug 3 - `sample_mvt` / `sample_student_t` reused the same JAX PRNG key

Both functions called `keras.random.normal(..., seed=seed)` and
`sample_mvn(..., seed=seed)` with the *same* integer `seed`. On TF/torch
a global counter advances between calls, so the two streams differ. On
JAX, an integer seed deterministically produces the same `PRNGKey` each
time -- so the numerator `z` and the chi-squared scaler `v` were
perfectly correlated, and "Student-T samples" collapsed to
`sign(z) * sqrt(dof)`. Empirically: kurtosis ~ 1 instead of ~9; variance
fixed at `dof` instead of `dof/(dof-2)`.

Fix: add a `_split_seed(seed, n)` helper that returns `[seed+i for i in
range(n)]`, then derive `(seed_z, seed_v)` so each downstream
`keras.random` call has its own key. Backwards-compatible with
`seed=None` (returns `[None]*n`, falling back to the backend's global
counter).

## Bug 4 - `compute_gradients` JAX path leaked tracers via `var.assign`

Structurally analogous to the torch bug fixed in `e5671a1`. The JAX
branch called `var.assign(<arr>)` inside the closure passed to
`jax.value_and_grad`. Under tracing, `<arr>` is a `Tracer`, and
`var.assign` writes it into the Variable's backing store. The reference
escapes the trace boundary -- after `value_and_grad` returns, `v.value`
is a `LinearizeTracer` instead of a concrete `ArrayImpl`. The next
iteration reads that tracer back, accumulating the autograd graph one
iteration at a time. The original code papered over this with a
"restore concrete values" reassign at the end, which worked but is
fragile and can OOM on long runs (analogous to the torch `.grad`
accumulation that pumped an A100 dry around iter 7).

Fix: bind the Variables only *inside* the closure, via Keras 3's
`StatelessScope` (the canonical mechanism for purifying Variable reads
during a JAX trace). The scope's `state_mapping=[(v, arr)]` rebinds
`v.value` to `arr` only for the body of `_loss`; outside, the
Variable's concrete value is untouched. No tracer ever lands in the
Variable, so the closing reassign is unnecessary and gone.

## Tests added

`tests/test_backend_multibackend.py` -- 14 tests across 5 classes:

  * `TestBug1SafeCholeskyJaxNaN` -- 3 tests: non-PSD input never NaNs,
    reconstruction is within jitter, strongly-negative eigenvalues
    still rescuable.
  * `TestBug2LgammaDifferentiable` -- 3 tests: value matches scipy,
    gradient matches digamma, `mvt_log_prob` has a nonzero, finite
    gradient w.r.t. dof.
  * `TestBug3StudentTSampling` -- 4 tests: Student-T variance,
    bimodality check (IQR(|x|) > 0.5), kurtosis > 4, multivariate
    variance per dim.
  * `TestBug4ComputeGradientsJaxMemory` -- 3 tests: no tracer in
    `v.value` after one grad call, 50-iter loop keeps Variable
    concrete, end-to-end `ParameterFitter.fit(..., max_n_iterations=50)`
    on a tiny GaussianPRF finishes with finite output.
  * `TestResidualFitterStudentT` -- 1 integration test: full
    `ResidualFitter.fit(method='t')` finishes with finite Omega and
    positive finite dof (cross-cuts Bugs 1 + 2 + 4).

All 14 tests pass locally under each of `KERAS_BACKEND={tensorflow,
jax, torch}`. Existing 197-test suite still green under TF.
